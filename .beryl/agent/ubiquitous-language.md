# Ubiquitous Language

| Business Term | Technical Symbol | Definition | Constraints | Avoid |
| --- | --- | --- | --- | --- |
| Design Concept | `DesignConcept` | The shared organizing model guiding architecture and implementation choices. | Must be coherent across contexts. | `Idea`, `GeneralModel` |
| Design Tree | `DesignTree` | Living map of open and settled decisions. | Updated when design moves. | `PlanDump` |
| Bounded Context | `BoundedContext` | A domain boundary with explicit ownership and language. | Owns its internal model and API. | `Module` (too generic) |
| Ubiquitous Language | `UbiquitousLanguage` | Shared domain vocabulary in docs and code. | Terms must be stable and explicit. | Ambiguous nouns like `Data` |
| Feedback Loop | `FeedbackLoop` | Generate-check-fix cycle using deterministic tools. | Must include real tool output. | `TryAgainLoop` |
| Success Check | `SuccessCheck` | Pre-coding acceptance condition that proves a plan, redirect, feature slice, or bug fix worked. | Must name the expected artifact, deterministic command, generated output or browser evidence when applicable, and at least one user-visible behavior. | Vague done criteria such as `LooksGood` |
| Commit Boundary | `CommitBoundary` | Proposed repo-history unit for implementation work. | Must have one purpose, expected files, and a validating check command; should not mix generated output, docs, tests, and source unless required. | Large mixed commit |
| Repository Upkeep | `RepositoryUpkeep` | Tracked process for routing ideas and materials into durable docs, temporary scratch state, task backlog, or archive/discard lanes. | Must keep repository files as source of truth and treat hidden chat history or ignored scratch context as non-authoritative. | Relying on `current.md` as the durable record |
| Material Intake | `MaterialIntake` | First classification step for deciding whether new context is durable, temporary, backlog-worthy, or discardable. | Must promote only the durable conclusion into the smallest relevant tracked file. | Copying raw task or chat material wholesale |
| Agent-Ready Repository | `AgentReadyRepository` | A repository with versioned agent instructions, task routing, deterministic checks, visible review artifacts, and clear human ownership before agent work begins. | Must be backed by repo files and commands, not only prompt advice. | `AI-enabled repo`, `Agentic vibe` |
| Hard Guarantee Layer | `HardGuaranteeLayer` | Repository-installed process controls that make agent expectations, checks, generated contracts, and review boundaries inspectable. | Guarantees process visibility and deterministic gates, not model correctness. | `Safety magic`, `Correctness guarantee` |
| Runtime Harness | `RuntimeHarness` | CLI, IDE, plugin, or execution environment that loads and runs an agent session. | Beryl may generate contracts for harnesses but does not own their runtime behavior. | Treating harness behavior as repository state |
| Skill Pack | `SkillPack` | Reusable runtime-loaded agent behavior instructions. | Useful beside Beryl; not the same as repository governance. | Calling Beryl just a skill pack |
| Understanding Artifact | `.beryl/artifacts/understanding/<timestamp>-<slug>/index.html` | Optional self-contained offline teaching page generated from structured explanation data. | Ignored by default; source-derived content is escaped passive text, has no external dependencies, and is removed after discussion unless explicitly kept. | A live repository dashboard |
| Driver Task Import | `.beryl/driver/import-github-issues.sh` | Driver utility that copies GitHub issues into numbered task briefs for `run.sh`. | Must preserve in-progress driver state and treat copied issue text as untrusted context. | Directly editing runtime `state/` as the source of truth |
| Task DAG | `TaskDAG` | Directed acyclic graph of selected driver tasks and required ordering dependencies. | Agent-proposed DAGs are untrusted until deterministic validation confirms node coverage, dependency integrity, and absence of cycles. | Treating model rationale as proof of independence |
| Driver Worktree Optimization | `.beryl/driver/optimize-worktrees.sh` | Optional preflight that asks an agent for a Task DAG, verifies it, computes parallel waves, and prepares Git worktrees for parallel-ready tasks. | Disabled by default; prepares worktrees but does not auto-run or auto-merge worker tasks in this slice. | Hidden parallel execution, implicit merge scheduling |
| GitHub Issue Finalization | `.beryl/driver/state/<id>/issue-finalize.txt` | Soft post-commit step that comments on and attempts to close a linked GitHub issue. | Must record comment/close outcome without failing an already verified local commit. | Treating GitHub availability as part of the local commit gate |
| Generated Output | `GeneratedOutput` | Built artifact, copied asset, static HTML, feed, sitemap, robots file, search index, or similar file users or crawlers receive. | Static-site changes must verify affected generated output, not source alone. | Source-only verification |
| Affected Test Gate | `.beryl/scripts/check-affected.sh` | Commit and manual check step that maps changed files to related tests or full-test fallback. | Must be deterministic and run through `.beryl/scripts/check.sh`. | Ad hoc local test picking |
| Full Test Fallback | `FULL_TEST_CMD` | Complete project test command used when a change is too broad to select related tests safely. | Configured in `.beryl/agent/affected-tests.conf`. | Silent skip for broad changes |
| Setup Script | `.beryl/scripts/setup-project.sh` | Local interactive or noninteractive onboarding frontend for the agent control plane. | Delegates one normalized lifecycle request to `install.sh`; it never independently copies components, writes locks, initializes Git, or changes hooks. | Independent installer |
| AI Agent Fallback | `run_agent_fallback` | Opt-in setup path that hands project-specific configuration to a selected headless coding agent. | Prompt must be user-provided and not stored in tracked files. | Hidden automation |
| Entropy Hotspot | `EntropyHotspot` | High-churn and high-complexity area likely to degrade maintainability. | Used for targeted refactoring. | `MessyFile` |
| Extraction Slice | `ExtractionSlice` | One safe, non-feature refactor step identified after reading changed files from a product run. | Must preserve behavior, avoid new features, name the files involved, and identify the protecting check or missing regression test. | Broad cleanup, opportunistic redesign |
| Vertical Slice | `VerticalSlice` | Smallest end-to-end behavior change through one boundary. | Must be testable in isolation. | `BigRefactor` |
| Adapter | `Adapter` | Boundary object that isolates external systems from domain logic. | Domain must not depend on vendor details. | `ServiceHelper` |
| Seam | `Seam` | Intentional change point for behavior substitution without invasive edits. | Should be protected by tests. | `HackPoint` |
| ADR | `ADR` | Architecture Decision Record for durable decisions. | Required for lasting boundary changes. | `RandomNote` |
| Beryl Root | `BERYL_ROOT` | Absolute path to the installed `.beryl` control-plane directory. | Use only for Beryl-owned implementation files and manifest/config reads. | Treating it as the host repo root |
| Repo Root | `REPO_ROOT` | Absolute path to the host project repository root that contains `.beryl`. | Use for Git operations, host scans, root shims, and test manifests. | Treating it as the Beryl implementation root |
| Component | `Component` | Installable Beryl capability such as `agent-core`, `checks`, `githooks`, `ci`, or `driver`. | Declared in `.beryl/beryl.components.json`; dependencies resolve before install. | Ad hoc copy bundle |
| Profile | `Profile` | Named component selection such as `minimal`, `standard`, or `full`. | Must resolve through the same dependency graph as explicit components. | Separate setup mode |
| Component Manifest | `ComponentManifest` | `.beryl/beryl.components.json`, the source of truth for components, profiles, paths, root contracts, and hooks. | Parsed by installer, setup, and validator. | Duplicated component lists |
| Agent Context Seed | `AgentContextSeed` | Generic template files copied into `.beryl/agent/` during install for project-owned brief, architecture, design, testing, vocabulary, and ADR context. | Must not contain Beryl's own product or architecture decisions. Existing target files are preserved unless the seed conflict policy allows overwrite. | Copying Beryl's development docs into target repos |
| Lifecycle Engine | `install.sh` | Public mutation interface for initial install, locked update, restore, conservative uninstall, explicit adoption, and standalone bootstrap. | Sole lifecycle engine for setup delegation; remote sources require a full 40-character commit SHA plus archive digest, and it validates paths without following symlinks. | Separate setup and install lifecycles |
| Lockfile | `.beryl/lock.json` | Installed component, immutable source identity, `expectedSourceSha256`, policy, and ownership record written after successful readiness verification. | Updates default to locked source ref, digest, and requested selection; digest-protected remote updates refuse absent or mismatched proof. | Hidden install state |
| Managed Path Ledger | `managedPaths` in `.beryl/lock.json` | File-level record of Beryl lifecycle state and rollback boundaries. | Not destructive authority: normal updates preserve deselected ambiguous paths and remove them from Beryl ownership. Explicit profile/component selection authorizes recovery cleanup. | Treating every `.beryl/` path as Beryl-owned |
| Update Preserve Paths | `updatePreservePaths` in `.beryl/beryl.components.json` | Manifest-declared exact paths and subtrees that an update must leave target-owned. | Includes canonical agent context, custom settings, driver configuration/tasks/state, and prior update backups; must remain under `.beryl/`. | A broad overwrite exclusion with no declared ownership |
| Lifecycle Transaction | `install.sh` operation | Target staged, validated transaction contract for initial install and update. | Validates lexical target plus every existing ancestor and leaf without following symbolic links, verifies a candidate lock then committed lock, and writes the lockfile last. Normal updates preserve deselected ambiguous paths. | In-place directory replacement |
| Recovery Lifecycle | `--restore`, `--uninstall`, `--adopt-existing` | Conservative operations governed by ADR 0010. | Restore requires explicit historical selection and current selection before current-only removal, then proves current source (and remote ref/digest before fetch). Uninstall requires explicit profile/components and removes only selected unchanged digest-proven paths. Adoption requires an identical unlocked surface and only infers minimal/standard/full when unambiguous. | Broad cleanup or implicit adoption |
| Readiness State | `ready`, `ready-with-preserved-external-contracts` | Lock-aware doctor outcome for an installed target. | Preserved-contract state names the external root/hook warning and states that Beryl does not enforce it; source checkout verification requires `--development`. | Silent green enforcement |
| Post-Transaction Bootstrap | `--bootstrap-agent` | Target opt-in external coding-agent action requested after lifecycle success. | Standalone, never transactional, because external mutations cannot be completely enumerated or rolled back. | Rollback-guaranteed bootstrap |
| Install Surface | `InstallSurface` | The ordered list of manifest-derived paths copied by installer mode and profile/component selection. | Must match what `install.sh --dry-run` and manifest dependency resolution both report. | Implicitly assuming copied file lists |
| Signed Release Bootstrap | `beryl-bootstrap.sh` | Versioned trust-root entry point that verifies signed release metadata and archive integrity before extracting and executing the selected installer. | Its public key must be independently trusted; it rejects expired metadata and never lets metadata choose arbitrary URLs. | An unauthenticated latest installer |
| Security Feature | `SecurityFeature` | A concrete mitigation that reduces agentic workflow attack surface and is tracked in docs or code. | Must name one user-visible control and at least one verifying check. | Vague security slogans |
| Agentic Security Surface | `AgenticSecuritySurface` | The set of command paths, prompts, and automation integrations where untrusted input can influence repository or shell behavior. | Guarded by input validation, command allowlists, and deterministic checks. | Raw prompt-to-shell assumptions |
| Initial Build | `InitialBuild` | The first coordinated implementation of a large or greenfield application requested from an installed Beryl repository. | Requires clarification, repository discovery, a ratified hierarchy, dependency-ordered work, and completion checks. | Treating every feature as an initial build |
| Hierarchy Plan | `HierarchyPlan` | The temporary, hierarchical execution plan for an active initial build, stored in `.beryl/agent/hierarchy.md`. | Git-tracked while active; created after ratification and deleted only after durable context promotion and completion checks. | Calling it permanent project documentation |
| Hierarchy Node | `HierarchyNode` | One dependency-aware deliverable in a `HierarchyPlan`. | Has a stable id, parent, dependencies, deliverable, acceptance checks, status, and canonical context targets. | Unordered task list |
| Plan Ratification | `PlanRatification` | The user's explicit approval of the proposed initial-build scope, hierarchy, and implementation plan. | Must happen before `hierarchy.md` is created or build edits begin. | Inferring approval from silence |
| Context Promotion | `ContextPromotion` | Moving durable decisions, boundaries, terms, and verification knowledge from temporary build notes into canonical agent Markdown. | Promote only facts needed by future work; keep progress and scratch rationale transient. | Copying the whole hierarchy into canonical docs |
| Initial Build Completion | `InitialBuildCompletion` | The lifecycle state reached when every hierarchy node and required check passes and durable context is promoted. | Only then may `hierarchy.md` be deleted. | Deleting the hierarchy when coding merely stops |
